# 🚀 راهنمای استقرار ویزیتو روی هاست اشتراکی cPanel (شتابان هاست)

این راهنما نصب **از صفر** نسخه Production ویزیتو روی هاست اشتراکی با کنترل‌پنل cPanel و
قابلیت **Setup Node.js App** را قدم‌به‌قدم توضیح می‌دهد.

| پیش‌نیاز | مقدار |
| --- | --- |
| Node.js | **24 (الزامی)** — نسخه 22 پشتیبانی نمی‌شود (بخش ۱ را ببینید) |
| دیتابیس | SQLite (فایل محلی — نیازی به MySQL نیست) |
| فایل راه‌انداز | `server.cjs` |
| دامنه | با SSL فعال (Let's Encrypt cPanel کافی است) |
| دسترسی Terminal | پلن‌های IRCP-04 / IRCP-05 (برای دستورهای نصب) |

> 💡 نکته کلیدی معماری: برنامه به‌صورت **Next.js Standalone** اجرا می‌شود و فایل راه‌انداز
> `server.cjs` خودش کارهای زیر را انجام می‌دهد: خواندن `.env`، بررسی/ساخت پوشه دیتابیس و
> داده‌ها، اجرای امن مهاجرت‌ها با قفل (موتور داخلی node:sqlite — بدون Prisma CLI)، و بالا آوردن سرور با **Node.js** (بدون Bun، بدون tee).

## ۰. دو مسیر استقرار — اول این را بخوانید

| | مسیر الف (پیشنهادی) — بسته آماده | مسیر ب — Build روی سیستم خودتان |
| --- | --- | --- |
| ورودی | `vizito-prod-<نسخه>.zip` (آماده اجرا) | سورس (ZIP یا Git) |
| روی هاست چه می‌شود؟ | فقط Extract + تنظیم env + Restart | Extract + `npm ci` + `npm run build` |
| Build روی هاست؟ | ❌ هیچ | ❌ **هرگز روی هاست Build نگیرید** (بخش ۷) |
| npm روی هاست؟ | ❌ لازم نیست | ✅ یک‌بار `npm ci` |
| مناسب برای | cPanel بدون ترمینال / اتصال آرام / اولین استقرار | توسعه و تغییر سورس |

> ⚠️ **چرا Build روی هاست ممنوع است؟** نسخه‌های جدید Next.js (مثلاً ۱۶.۴.۳) باینری SWC دارند
> که به GLIBC 2.29/2.30 نیاز دارد؛ GLIBC هاست شما 2.28 است ⇒ Build با خطای
> `GLIBC_2.29 not found` شکست می‌خورد و `.next/standalone` ساخته نمی‌شود.
> در نسخه فعلی Next.js دقیقاً روی **16.1.3 قفل شده** (SWC آن فقط GLIBC 2.17 می‌خواهد —
> با objdump روی باینری تأیید شده) و تمام Build‌ها باید روی سیستم شما (ویندوز/لینوکس) اجرا شود.

## ۱. انتخاب نسخه Node.js

در cPanel وارد **Setup Node.js App** شوید (یا «Select Node.js Version» بسته به قالب پنل):

- نسخه **24** را انتخاب کنید — **الزامی**.
- ⚠️ چرا Node 22 کافی نیست؟ وابستگی `html2canvas-pro@2.5.2` (خروجی PDF گزارش‌ها) رسماً
  `node >= 24` می‌خواهد؛ به همین دلیل `engines` پروژه روی `>=24.0.0` است و فایل راه‌انداز
  `server.cjs` هم روی Node پایین‌تر از ۲۴ با پیام واضح متوقف می‌شود.
- نسخه‌های بالاتر (۲۶ و بعد) اگر در پنل ارائه شد، پیش از استفاده باید جداگانه تست شوند.
- `Application mode` = **Production**
- `Application root` = `vizito` (یعنی `/home/USERNAME/vizito` — می‌توانید نام دیگری بگذارید)
- `Application URL` = دامنه یا زیردامنه‌ای که سایت روی آن است (مثلاً `app.yourdomain.com`)
- `Application startup file` = **`server.cjs`**

فعلاً روی **Create** نزنید اگر می‌خواهید اول فایل‌ها را آپلود کنید؛ یا اگر ساخته‌اید، در ادامه تنظیم می‌کنیم.

## ۲. آپلود فایل‌ها

**مسیر الف (بسته آماده):** فایل `vizito-prod-<نسخه>.zip` را در File Manager آپلود و داخل `/home/USERNAME/vizito` Extract کنید.
این بسته شامل خروجی Standalone کامل (با موتورهای Prisma و sharp لینوکسی)، `server.cjs`، مهاجرت‌ها و مستندات است —
**نیازی به npm install و build نیست؛ مستقیم به بخش ۵ (env) بروید.**

**مسیر ب (سورس):** سورس را به یکی از این دو روش به `/home/USERNAME/vizito` برسانید:

**روش الف — Git (پیشنهادی):** از Terminal:

```bash
cd /home/USERNAME
git clone <آدرس-مخزن-شخصی-شما> vizito
cd vizito
```

**روش ب — ZIP:** فایل ZIP استقرار (بدون `node_modules` و بدون فایل‌های حساس) را در File
Manager آپلود و در همان پوشه Extract کنید.

> ⚠️ فایل ZIP رسمی استقرار **نباید** شامل `.env`، `db/*.db`، `keys/`، `android/keystore/`
> و `node_modules` باشد. اگر ZIP دیگری دارید که این‌ها را دارد، آن‌ها را حذف کنید.

## ۴. نصب وابستگی‌ها با npm — فقط مسیر ب

> ⛔ اگر «مسیر الف» (بسته آماده) را آپلود کرده‌اید، این بخش و بخش ۷ را **رد کنید** — روی هاست هیچ npm/build لازم نیست.

در cPanel → Setup Node.js App دکمه **Run NPM Install** را بزنید، یا در Terminal:

```bash
cd /home/USERNAME/vizito
npm ci        # دقیقاً همان نسخه‌های package-lock.json — هرگز npm install خالی نزنید
```

> بعد از نصب، اسکریپت `postinstall` به‌صورت خودکار **Prisma Client** را generate می‌کند
> (با binaryTargets هاست — موتورهای rhel/debian-openssl-1.1.x هم دانلود می‌شوند).

## ۵. تنظیم Environment Variables

در صفحه Setup Node.js App بخش **Environment variables** این‌ها را اضافه کنید
(توضیح کامل هر متغیر در `.env.example` پروژه هست):

| متغیر | الزامی؟ | مقدار روی هاست شما |
| --- | --- | --- |
| `DATABASE_URL` | ✅ الزامی | `file:/home/USERNAME/vizito_data/vizito.db` |
| `VIZITO_DATA_DIR` | 🔴 به‌شدت توصیه‌شده | `/home/USERNAME/vizito_data` |
| `BACKUP_ENCRYPTION_KEY` | ✅ برای پشتیبان‌گیری | حداقل ۳۲ کاراکتر تصادفی — تولید: `openssl rand -base64 48` |
| `SETUP_TOKEN` | ✅ فقط برای نصب تازه | کد تصادفی قوی — تولید: `openssl rand -hex 24` |
| `OWNER_MOBILES` | اختیاری | موبایل‌های سازنده با کاما (دسترسی همیشگی) |
| `OWNER_SETUP_KEY` | فقط با OWNER_MOBILES | کلید تصادفی قوی |
| `TRUSTED_PROXY_HOPS` | اختیاری | `1` (پیش‌فرض Passenger روی cPanel) |
| `VIZITO_ALLOWED_ORIGINS` | اختیاری | مبدأهای مجاز اضافی برای ضد CSRF — فقط اگر برنامه در iframe پنل دیگری باز می‌شود؛ wildcard پسوندی: `*.example.com` |
| `LICENSE_PUBLIC_KEY_PEM` | معمولاً خالی | فقط برای چرخش کلید عمومی |
| `LICENSE_PRIVATE_KEY_PEM` | ❌ روی سرور مشتری نگذارید | فقط سرور سازنده |

> 🔐 `PORT` و `HOSTNAME` را دستی تنظیم **نکنید** — Passenger خودش می‌گذارد.
>
> به‌جای پنل می‌توانید همین مقادیر را در فایل `.env` کنار پروژه هم بگذارید
> (`server.cjs` آن را می‌خواند؛ ولی متغیرهای پنل همیشه اولویت دارند).

## ۶. مهاجرت‌های دیتابیس — خودکار (بدون Prisma CLI)

> ✅ لازم نیست دستی چیزی بزنید: `node server.cjs` (فایل راه‌انداز cPanel) **هر بار قبل از بالا آمدن**
> مهاجرت‌ها را با موتور داخلی `node:sqlite` و با قفل فایلی اجرا می‌کند:
> - مهاجرت اعمال‌نشده ⇒ اجرا و ثبت (سازگار با جدول `_prisma_migrations` خود Prisma)
> - دیتابیسِ ساخته‌شده با `db push` (بدون رکورد مهاجرت) ⇒ به‌صورت امن **baseline** می‌شود؛
>   تراکنش ROLLBACK می‌شود و «هیچ داده‌ای دست نمی‌خورد»
> - خطای دیگر ⇒ سرور بالا نمی‌آید و خطا کامل در لاگ دیده می‌شود
> - هر مهاجرت داخل BEGIN…COMMIT است ⇒ اجرای نیمه‌کاره ممکن نیست
>
> اجرای دستی (اختیاری):
>
> ```bash
> cd /home/USERNAME/vizito
> export DATABASE_URL="file:/home/myvizito/vizito/data/azhivan.db"
> node scripts/migrate-sqlite.cjs     # یا: npm run db:migrate:prod
> ```
>
> روی سیستم توسعه هم `npx prisma migrate deploy` همان مهاجرت‌ها را اعمال می‌کند.
>
> ❌ از `prisma db push` در Production استفاده نکنید (فقط توسعه) و هرگز
> `prisma migrate reset` یا `db push --accept-data-loss` روی هاست اجرا نشود.

## ۷. ساخت خروجی Production — فقط روی سیستم خودتان (نه هاست)

> ⛔ روی هاست هرگز `next build` نگیرید (گلیبک — بخش ۰). Build فقط روی ویندوز/لینوکس خودتان:

```bash
# روی سیستم شما (ویندوز یا لینوکس) — Docker لازم نیست (خطای 403 داکرهاب بی‌ربط است):
npm ci                 # نصب دقیق طبق lockfile
npm run build          # prisma generate + next build + بسته‌بندی Standalone
npm run deploy:package # ساخت download/vizito-prod-<نسخه>.zip — آماده آپلود به cPanel
```

- Build روی ویندوز مشکلی ندارد: SWC فقط «زمان Build» لازم است (نسخه ویندوزی آن نصب می‌شود) و
  موتورهای لینوکسی Prisma/sharp طبق `binaryTargets` و `outputFileTracingIncludes` داخل Standalone قرار می‌گیرند.
- خروجی `vizito-prod-<نسخه>.zip` شامل همه‌چیز به‌جز فایل‌های حساس است (`.env`، `keys/`، `db/` هیچ‌وقت داخلش نیست).

## ۸. راه‌اندازی برنامه

در صفحه Setup Node.js App دکمه **Restart** را بزنید. cPanel از فایل راه‌انداز
`server.cjs` استفاده می‌کند که به‌ترتیب:

1. `.env` را می‌خواند (بدون بازنویسی متغیرهای پنل)
2. مسیر `DATABASE_URL` را چک می‌کند: مطلق بودن، ساخت پوشه، تست قابل‌نوشتن‌بودن
3. `VIZITO_DATA_DIR` را می‌سازد/چک می‌کند
4. هشدار واضح برای متغیرهای امنیتی جاافتاده می‌دهد
5. مهاجرت‌ها را با موتور داخلی node:sqlite و با قفل اجرا می‌کند (شکست ⇒ بالا نیامدن؛ baseline امن برای دیتابیس‌های db-push)
6. سرور Next.js Standalone را با node اجرا می‌کند (روی PORT ای که Passenger می‌دهد)

اجرای دستی از ترمینال هم ممکن است:

```bash
cd /home/USERNAME/vizito
npm start        # = node server.cjs
```

## ۹. بررسی لاگ‌ها

- در صفحه Setup Node.js App بخش **Log** (یا دکمه باز کردن لاگ Passenger) خطاهای اجرا را ببینید.
- در Terminal: `tail -f /home/USERNAME/logs/<دامنه>.error.log` (مسیر بسته به پنل ممکن است متفاوت باشد)
- `server.cjs` خودش پیام‌های `[vizito]` چاپ می‌کند (وضعیت مهاجرت، هشدارها).
- رمز عبور/کلید/توکن هرگز در لاگ نوشته نمی‌شود.

**خطاهای رایج:**

| پیام | معنی و راه‌حل |
| --- | --- |
| `Node.js ... پشتیبانی نمی‌شود (حداقل نسخه: 24)` | نسخه Node در پنل را روی **24** بگذارید و Restart بزنید (بخش ۱) |
| `DATABASE_URL تنظیم نشده` | متغیر محیطی را در پنل ست کنید (بخش ۵) |
| `مسیر دیتابیس باید مطلق باشد` | مقدار باید `file:/home/...` باشد نه `file:./db/...` |
| `خروجی Standalone پیدا نشد` | `npm run build` را اجرا نکرده‌اید |
| `پوشه ... قابل نوشتن نیست` | دسترسی پوشه `vizito_data` را به user هاست بدهید (`chown`) |
| `migrate deploy ناموفق بود` | متن خطای بالای همان لاگ را ببینید (معمولاً دسترسی/مسیر) |
| `OWNER_KEY_REQUIRED` هنگام ثبت‌نام سازنده | یعنی یا `OWNER_SETUP_KEY` روی هاست تنظیم نشده، یا کلید وارد‌شده با آن فرق دارد. لاگ سرور خط `register owner-key diag: {"ownerMobile":true,"expectedSet":…,"provided":…,"match":…}` را نشان می‌دهد: اگر `expectedSet:false` است ⇒ متغیر `OWNER_SETUP_KEY` را در پنل اضافه کنید و Restart بزنید؛ اگر `match:false` است ⇒ کلید را درست وارد کنید. (در لاگ فقط وضعیت بولی ثبت می‌شود — هیچ مقداری لاگ نمی‌شود) |

## ۱۰. اتصال دامنه و SSL

1. دامنه/زیردامنه را در بخش **Domains** cPanel به هاست متصل کنید (Application URL در بخش Node هم همان باشد).
2. از بخش **SSL/TLS Status** گزینه **Run AutoSSL** را بزنید تا Let's Encrypt فعال شود.
3. با `https://دامنه-شما` باز کنید — کوکی نشست فقط روی HTTPS با پرچم `Secure` صادر می‌شود.

## ۱۱. ساخت حساب مدیر اولیه

روی نصب تازه، اولین ثبت‌نام فقط با **کد راه‌اندازی اولیه** ممکن است:

1. به `https://دامنه-شما` بروید → «ثبت‌نام».
2. فرم را پر کنید و در فیلد **کد راه‌اندازی اولیه** مقدار `SETUP_TOKEN` را وارد کنید
   (همان مقداری که در بخش ۵ تنظیم کردید).
3. این کاربر **مدیر** می‌شود و به‌صورت خودکار ۲۴ ساعت دوره آزمایشی می‌گیرد.
4. ثبت‌نام‌های بعدی فقط با **کد دعوت** مدیر (بخش «کاربران») ممکن است.

> - اگر `SETUP_TOKEN` تنظیم نشده باشد، اولین ثبت‌نام با پیام «کد راه‌اندازی اولیه نادرست است» رد می‌شود.
> - دو درخواست هم‌زمان حتی اگر با هم بزنید فقط یکی مدیر می‌شود (رزرو اتمیک در دیتابیس).
> - اگر شماره سازنده دارید: `OWNER_MOBILES` + `OWNER_SETUP_KEY` را ست کنید و با همان فرم ثبت‌نام کنید — دسترسی همیشگی بدون لایسنس می‌گیرید.
> - **سیاست سازنده (از نسخه ۱.۰.۸):** ثبت‌نام معتبر سازنده (شماره ∈ `OWNER_MOBILES` + کلید درست)
>   «همیشه» حساب **ADMIN** می‌سازد — حتی اگر دیتابیس از قبل کاربر داشته باشد. اگر قبلاً با همان شماره
>   حسابی وجود داشته باشد، همان حساب به‌صورت اتمیک به ADMIN ارتقا می‌یابد + رمز بر اساس همین فرم
>   بازنشانی و نشست‌های قبلی باطل می‌شوند. این مسیر هیچ راه ارتقایی برای کاربران عادی نمی‌سازد
>   (هر دو شرط سمت سرور لازم است).
> - بعد از ساخت مدیر، حذف `SETUP_TOKEN` از پنل امن‌تر است (فقط برای «نصب تازه بعدی» دوباره لازمش می‌کنید).

## ۱۳. پشتیبان‌گیری و بازیابی

### تهیه نسخه
- **دستی:** از داخل برنامه با حساب مدیر → بخش «پشتیبان‌گیری» → «تهیه نسخه جدید».
- **خودکار:** همان بخش، زمان‌بندی روزانه/هفتگی/ماهانه را فعال کنید. زمان‌بند داخل خود
  برنامه اجرا می‌شود (هر ۶۰ ثانیه چک می‌کند) و تا وقتی برنامه بالا است کار می‌کند —
  نیازی به Cron Jobs ندارد.
- فایل‌ها در `VIZITO_DATA_DIR/backups` ذخیره می‌شوند (خارج از وب) و با
  `BACKUP_ENCRYPTION_KEY` رمزنگاری می‌شوند.

### محدودیت صادقانه زمان‌بند
زمان‌بند داخل پروسه Node اجرا می‌شود؛ روی cPanel معمولاً یک پروسه وجود دارد و مشکلی
پیش نمی‌آید. اگر روزی **بیش از یک نمونه** از برنامه را روی یک دیتابیس اجرا کنید، ممکن است
برای یک بازه، دو نسخه خودکار ساخته شود (خطرناک نیست؛ فقط فایل تکراری است) — در آن
حالت یکی از نمونه‌ها را خاموش کنید یا زمان‌بندی را فقط در یکی فعال کنید.

### بازیابی
فایل پشتیبان رمزنگاری‌شده است؛ برای بازگشایی (روی سیستم شما یا سرور):

```bash
BACKUP_ENCRYPTION_KEY="همان-کلید-سرور" npm run backup:decrypt -- /مسیر/فایل-پشتیبان.json -o restored.json
```

خروجی `restored.json` شامل جدول‌های برنامه است. برای بازیابی کامل روی نصب تازه:

1. نصب تازه ویزیتو را بالا بیاورید (بخش‌های ۱ تا ۸) — دیتابیس خالی.
2. محتوای جدول‌های `restored.json` را مطابق همان ساختار وارد دیتابیس کنید
   (با Prisma یا ابزار SQLite) — ترتیب پیشنهادی: `users` ← `productGroups` ← `products`
   ← `customers` ← `orders` ← `orderItems` ← `payments` ← `notifications` ← `settings`.
3. یا ساده‌تر: از سازنده برنامه بخواهید نسخه را برایتان بازگرداند (فایل و کلید هر دو نزد شماست).

> 🔐 نسخه پشتیبان را **خارج از هاست** هم نگه دارید (دانلود از پنل برنامه و ذخیره در جای امن).
> اگر `BACKUP_ENCRYPTION_KEY` را از دست بدهید، فایل‌های پشتیبان قبلی بازگشایی نمی‌شوند.

## ۱۴. به‌روزرسانی نسخه بعدی (Deploy دوباره)

**مسیر الف (بسته آماده):**

1. فایل `vizito-prod-<نسخه-جدید>.zip` را آپلود و در همان پوشه Extract کنید (فایل‌های جدید جایگزین می‌شوند).
2. `.env` و دیتابیس چون در ZIP نیستند، دست‌نخورده می‌مانند.
3. در cPanel دکمه **Restart** را بزنید — مهاجرت‌های جدید (اگر باشد) در همان Restart به‌صورت امن اعمال می‌شوند.

**مسیر ب (سورس):**

```bash
cd /home/USERNAME/vizito
git pull            # یا آپلود/extract فایل ZIP سورس جدید
npm ci              # اگر package.json تغییر کرده
npm run build       # فقط روی سیستم خودتان! (بخش ۷)
# در cPanel دکمه Restart را بزنید (یا npm start در ترمینال)
```

دیتابیس و پشتیبان‌ها چون در `vizito_data` (یا `data/`) هستند دست‌نخورده می‌مانند.

## ۱۵. نکات امنیتی مخصوص هاست اشتراکی

- `vizito_data` باید بیرون از `public_html` باشد ⇒ هیچ‌کس از وب به دیتابیس/پشتیبان دسترسی ندارد.
- دسترسی پوشه‌ها را روی `750` و فایل‌های حساس را روی `600` نگه دارید:
  ```bash
  chmod 600 /home/USERNAME/vizito/.env   # اگر .env دارید
  ```
- فایل `keys/` و `android/keystore/` را روی هاست مشتری **نداشته باشید** (فقط سیستم سازنده).
- گزارش خطاهای برنامه Stack Trace افشا نمی‌کند (پیام‌های عمومی فارسی) — لاگ کامل فقط سمت سرور.
- `x-forwarded-for` فقط با `TRUSTED_PROXY_HOPS=1` (Passenger) تفسیر می‌شود؛ اگر فایروال/CDN دیگری جلوی هاست است، تعداد لایه‌ها را با پشتیبانی هاست چک کنید.

## ۱۶. اگر Terminal ندارید (پلن‌های پایین‌تر)

بدون Terminal هم می‌شود، سخت‌تر:

1. ZIP را در File Manager آپلود/Extract کنید.
2. **Run NPM Install** از صفحه Setup Node.js App (معادل `npm install`).
3. مهاجرت و build نیاز به اجرای دستور دارند — این دو را می‌توانید موقتاً در فایل
   `server.cjs` از طریق «startup» جا بدهید (برنامه خودش قبل از شروع migrate می‌کند)
   ولی **build باید یک‌بار جایی اجرا شده باشد**. اگر هاست امکان build نمی‌دهد:
   build را روی سیستم خودتان اجرا کنید و پوشه‌های `.next` (شامل `.next/standalone` کامل)
   و `node_modules` حاصل از `npm ci` روی همان سیستم‌عامل لینوکسی را در ZIP بگنجانید و آپلود کنید.
4. برای اجرای دستورهای یک‌باره، از پشتیبانی هاست بخواهید یا موقتاً Script داخلی تعریف کنید.

> ✅ توصیه: از پلن دارای Terminal (IRCP-04/IRCP-05) استفاده کنید — همه مراحل بالا مستقیم قابل اجراست.
