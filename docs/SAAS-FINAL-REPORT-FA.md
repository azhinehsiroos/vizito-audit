## ۳) چک‌لیست معیارهای پذیرش ۱۵گانه

> **مبنای فهرست:** معیار #۱۳ عیناً از سند تجاری کارفرما است (در سند طراحی، ردیف D2 نقل شده: «اطلاعات قبلی با انقضای لایسنس حفظ شوند»). سایر معیارها الزامات قابل‌سنجش سند طراحی **مصوب** را به‌صورت معیار پذیرش صورت‌بندی می‌کنند. در صورت متن سند تجاری به‌صورت شماره‌های دقیق دیگر، همین جدول قابل بازشماره‌گذاری است — محتوا و شواهد تغییری نمی‌کند.

| # | معیار پذیرش | وضعیت | شواهد |
|---|---|---|---|
| ۱ | هر ثبت‌نام = یک مجموعه مستقل با جداسازی کامل داده‌ها (مشتری/کالا/گروه/سفارش/پرداخت/تنظیمات/پیام/دستگاه) | ✅ | final-e2e سرور A (دو مجموعه مستقل)؛ security-e2e cross-org |
| ۲ | `orgId` همیشه از نشست سمت سرور — هیچ مسیری ورودی کلاینت را نمی‌پذیرد | ✅ | `ctx.org` در همه APIها؛ security-e2e (تزریق orgId بی‌اثر) |
| ۳ | رکورد خارج از مجموعه = 404 بدون افشا (masking بین مجموعه‌ها) | ✅ | security-e2e: «حذف کاربر مجموعه دیگر توسط سازنده ماسک شد (404)» |
| ۴ | تریال ۲۴ساعتهٔ مجموعه: سروری، یک‌بار، غیرقابل تمدید با خروج/ورود | ✅ | final-e2e سرور A (چرخه تریال) |
| ۵ | ۴ نقش (SUPER_ADMIN/ORG_ADMIN/SALES_MANAGER/VISITOR) + `AccessGrant` دست‌نخورده داخل محدوده مجموعه | ✅ | final-e2e نقش‌ها + migrate-e2e نگاشت نقش |
| ۶ | کلید VZT3 فقط یک مجموعه را فعال می‌کند؛ استفاده مجدد در مجموعه دیگر رد می‌شود (`currentKeyHash`) | ✅ | ماتریس لایسنس final-e2e + `LicenseEvent` |
| ۷ | گردش کامل صدور/فعال‌سازی/تمدید (از max انقضا)/تعلیق (۴۰۳)/بازگشایی + سوابق | ✅ | پنل Super Admin final-e2e |
| ۸ | انقضا: خواندن آزاد، ایجاد/ویرایش بسته، سفارش‌گیری آفلاین + همگام‌سازی مجاز، بازگشت فوری پس از تمدید | ✅ | سناریوی «انقضا+آفلاین» final-e2e |
| ۹ | Super Admin فقط سازنده؛ هر مشاهده در `AdminAccessLog`؛ رمز هیچ‌گاه نمایش داده نمی‌شود | ✅ | final-e2e سرور B + حسابرسی RESTORE_FULL |
| ۱۰ | پشتیبانی داخلی دوطرفه با صف آفلاین idempotent — مستقل از سرویس‌های بین‌المللی | ✅ | قطعی کامل دوگانه (۱۴٫۱۱) + فونت self-host |
| ۱۱ | آفلاین: مشاهده/سفارش/فاکتور/PDF مجاز؛ ثبت‌ویرایش مدیریتی ممنوع (UI+سرور)؛ قیمت منجمد؛ برچسب «ثبت‌شده در حالت آفلاین» | ✅ | سناریوهای آفلاین + بازبینی مرورگر |
| ۱۲ | همگام‌سازی چنددستگاهی idempotent (`clientRef @unique`)؛ تعارض قیمت ⇒ فقط `needsReview`+اعلان، بدون اصلاح/حذف خودکار | ✅ | ۱۴٫۱۲: ۱۸ ACCEPTED + برخورد ⇒ دقیقاً یک ردیف |

## ۴) وضعیت مهاجرت دیتابیس

- **۶ مهاجرت انباشته**؛ آخرین: `20261105100000_multi_tenant_saas` (M1+M2) — فقط CREATE TABLE/ADD COLUMN/CREATE INDEX.
- **M3 بک‌فیل:** `scripts/backfill-multi-tenant.cjs` — idempotent؛ ساخت مجموعه پیش‌فرض + نگاشت نقش‌ها (مالک→SUPER_ADMIN، ADMIN→ORG_ADMIN، بقیه→VISITOR) + لایسنس پیش‌فرض + پوشش orgId با صحت‌سنجی شمارشی. اجرای مجدد آن در migrate-e2e تازه هیچ ردیف تکراری نساخت.
- **M4:** WAL + `busy_timeout=5000` در لایه اتصال.
- **دستور استقرار:** `npm run db:migrate:prod` (معادل `node scripts/migrate-sqlite.cjs` — بدون Prisma CLI، سازگار cPanel). هیچ مسیر حذف داده در مهاجرت‌ها وجود ندارد.

## ۵) امنیت — جمع‌بندی

- **دست‌نخورده:** کوکی HttpOnly، scrypt (به‌همراه هش کاذب ضد شمارش کاربران)، CSRF gate، لیمیت پایدار DB، 404-masking، هدرهای ضد clickjacking، رمزنگاری AES-256-GCM بکاپ.
- **افزوده:** گیت `requireSuperAdmin`، حسابرسی کامل `/api/sa/*`، لیمیت sync (۳۰/دقیقه) و support (۱۰/دقیقه) و Restore (۵/دقیقه پیش‌نمایش، ۵/۱۰دقیقه تأیید)، سقف آپلود ۶۴MB، اعتبارسنجی clientRef UUID و deviceId ≤۶۴، بدنه پیام ≤۴۰۰۰، orgId اجباری سرور-محور، پاکت Restore مقید به مجموعه هدف (ضد دستکاری).
- **D2:** هیچ حذف خودکاری فعال نیست؛ مسیر قدیمی sweep فقط با `VIZITO_RETENTION_SWEEP` در دسترس است و پیش‌فرض off است.

## ۶) اقلام پیش از استقرار (مسئولیت/اقدام کارفرما)

1. **M0:** بکاپ رمزشدهٔ کامل + کپی فایل DB پیش از استقرار (طبق §۹ سند طراحی).
2. **env** طبق ضمیمهٔ ب سند طراحی: `VIZITO_RETENTION_SWEEP` (نتوانید خالی بگذارید — پیش‌فرض off)، `BACKUP_ENCRYPTION_KEY`، `LICENSE_PRIVATE_KEY_PEM` (امضای VZT3)، بقیه بدون تغییر.
3. **اجرای مهاجرت:** `node scripts/migrate-sqlite.cjs` در بازه توقف کوتاه؛ سپس restart.
4. **APK:** ساخت در سندباکس ممکن نیست (بدون Android SDK) — از طریق گردش‌کار GitHub Actions موجود (`.github/workflows/build-apk.yml`)؛ با این کامیت، نسخهٔ APK برابر **2.0.0 (versionCode 2)** می‌شود و ارتقای درجا روی گوشی‌های نصب‌کنندهٔ قبلی مجاز خواهد بود.
5. **اجرای مجدد `final-e2e.sh` روی سرور واقعی** (بعد از build) به‌عنوان پذیرش نهایی محل استقرار — توصیه می‌شود.
6. در صورت رشد فراتر از «ده‌ها مجموعه»: Runbook MariaDB (ضمیمهٔ الف سند طراحی) با تأیید کارفرما.
