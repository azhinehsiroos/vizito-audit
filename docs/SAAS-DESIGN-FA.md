## ۱) مدل چندمجموعه‌ای (Tenancy)

### ۱.۱ اصل بنیادی
- هر مشتریِ ثبت‌نام‌شده = یک **مجموعه (Org)** مستقل با `id` یکتا (cuid).
- **همه** داده‌های تجاری به `orgId` گره می‌خورند: مشتریان، کالاها، گروه‌ها، سفارش‌ها، اقلام، پرداخت‌ها، تنظیمات، پیام‌های پشتیبانی، دستگاه‌ها.
- `orgId` همیشه از **نشست سمت سرور** (`ctx.org`) استخراج می‌شود — **هرگز از ورودی کلاینت خوانده نمی‌شود**؛ تغییر شناسه در request هیچ اثری ندارد.
- تمام کوئری‌های GET/POST/PUT/DELETE به‌صورت سیستمی `orgId` را فیلتر می‌کنند؛ رکورد خارج از مجموعه = **404** (همان الگوی 404-masking موجود، حالا بین مجموعه‌ها).
- کنترل دسترسی ۱۰۰٪ سمت سرور؛ UI فقط نمایشی است.

### ۱.۲ مدل داده جدید

```prisma
model Org {
  id               String    @id @default(cuid())
  name             String                 // نام مجموعه
  logo             String?                // data URL (مهاجرت از Setting.app_logo)
  inviteCode       String?                // کد دعوت اختصاصی مجموعه (مهاجرت از Setting)
  status           String    @default("ACTIVE") // ACTIVE | SUSPENDED
  suspendedAt      DateTime?
  // تریال ۲۴ساعته مجموعه — سمت سرور نوشته می‌شود و هرگز تمدید نمی‌شود
  trialStartsAt    DateTime?
  trialEndsAt      DateTime?
  license          License?
  createdAt        DateTime  @default(now())
  updatedAt        DateTime  @updatedAt
}

model License {
  id            String   @id @default(cuid())
  orgId         String   @unique
  org           Org      @relation(fields: [orgId], references: [id], onDelete: Restrict)
  plan          String   // D30 | D90 | D180 | D365 | PERM
  startsAt      DateTime
  expiresAt     DateTime?   // null فقط برای PERM
  status        String   @default("ACTIVE") // ACTIVE | SUSPENDED
  source        String   @default("KEY")    // KEY (کلید امضاشده) | ADMIN (صدور مستقیم سازنده)
  currentKeyHash String? // SHA-256 کلید فعال — ضد استفاده مجدد در مجموعه دیگر
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  events        LicenseEvent[]
}

model LicenseEvent {          // تاریخچه صدور/فعال‌سازی/تمدید/تعلیق
  id        String   @id @default(cuid())
  orgId     String
  org       Org      @relation(fields: [orgId], references: [id], onDelete: Cascade)
  type      String   // ISSUE | ACTIVATE | EXTEND | SUSPEND | RESUME | EXPIRE_NOTICE
  plan      String?
  days      Int?     // برای EXTEND
  actorName String?  // سازنده/سیستم
  note      String?
  createdAt DateTime @default(now())

  @@index([orgId, createdAt])
}
```

### ۱.۳ نقش‌ها و کاربران

```prisma
model User {  // تغییرات نسبت به فعلی
  orgId    String?   // null فقط برای SUPER_ADMIN (سازنده)
  org      Org?      @relation(...)
  role     String    // SUPER_ADMIN | ORG_ADMIN | SALES_MANAGER | VISITOR  (رشته‌ای = قابل توسعه بدون مهاجرت)
  // kind و role قدیمی در طول مهاجرت به role جدید نگاشت می‌شوند و ستون‌های قدیمی یک نسخه حفظ می‌شوند
}
```

| نقش | تعریف | دسترسی پایه |
|---|---|---|
| `SUPER_ADMIN` | سازنده Vizito (بوت‌استرپ از `OWNER_MOBILES` + `OWNER_SETUP_KEY` موجود) | پنل مرکزی + معافیت دائمی از لایسنس/ترِیال؛ `isOwnerMobile` همچنان سپر دومی |
| `ORG_ADMIN` | مدیر اصلی مجموعه (سازنده ثبت‌نام) | مدیریت کاربران مجموعه، همه بخش‌های تجاری مجموعه؛ مشمول لایسنس/ترِیال مجموعه |
| `SALES_MANAGER` | مدیر فروش | بخش‌های تجاری بدون مدیریت کاربران (با `AccessGrant` قابل تنظیم دقیق) |
| `VISITOR` | ویزیتور | سکشن‌های اعطایی از طریق `AccessGrant` (سیستم موجود دست‌نخورده می‌ماند) |

- **تفسیر «مدیر اصلی سازنده از محدودیت لایسنس مستثنا باشد»:** منظور مدیر کلِ سازنده (SUPER_ADMIN) است؛ مدیر مجموعه مشمول لایسنس مجموعه خودش است. (در صورت تفسیر دیگر، کارفرما اصلاح کند.)
- `AccessGrant` فعلی بدون تغییر می‌ماند و فقط داخل محدوده مجموعه معنا پیدا می‌کند.
- **محدودیت تعداد کاربران:** فیلد آماده‌سازی در License قرار می‌گیرد (`maxUsers Int?`) اما **اجرا نمی‌شود** — طبق سند فقط با تأیید کارفرما در آینده فعال می‌شود.

### ۱.۴ ثبت‌نام آزاد
- ثبت‌نام (موبایل + نام + شرکت + رمز) ⇒ ایجاد `Org` + کاربر `ORG_ADMIN` + تریال ۲۴ساعته مجموعه (نوشته سمت سرور، یک‌بار، غیرقابل تمدید) — همان امنیت فعلی (لیمیت‌های پایدار DB، موبایل-یونیک سراسری).
- اولین مدیر نصب و حساب سازنده: همان جریان فعلی SETUP_TOKEN/OWNER_SETUP_KEY (دست‌نخورده).

## ۲) لایسنس مستقل هر مجموعه

- **کلید VZT3 (Ed25519 — توسعه سیستم فعلی VZT2):** payload `{v:3, o:orgId, e:expiryEpoch|0, p:plan}` — گره‌خوردگی به مجموعه به‌جای installId ⇒ یک کلید فقط یک مجموعه را فعال می‌کند (تطبیق `o` هنگام فعال‌سازی + ثبت `currentKeyHash` ضد استفاده مجدد).
- **مدت‌های قابل صدور:** ۳۰/۹۰/۱۸۰/۳۶۵ روز + نامحدود (PERM) — به‌عنوان plan.
- **گردش کار:** صدور (پنل سازنده یا کلید امضاشده) ← فعال‌سازی (صفحه لایسنس مجموعه با کلید) ← تمدید (`EXTEND` از max(انقضای فعلی، امروز) — همان منطق شارژ فعلی) ← تعلیق (`SUSPENDED`: کل APIهای تجاری 403؛ فقط پشتیبانی و مشاهده وضعیت) ← فعال‌سازی مجدد (`RESUME`).
- **انقضا (سمت سرور، بدون اتکا به UI):**
  - خواندن اطلاعات مجموعه: مجاز (داده هرگز حذف/قفل‌نشدنی نیست).
  - ایجاد/ویرایش اطلاعات پایه (کالا، گروه، مشتری، قیمت، تخفیف، کاربر، تنظیمات): **مسدود**.
  - سفارش‌گیری آفلاین و همگام‌سازی سفارش‌های ثبت‌شده روی دستگاه: **مجاز** (طبق بخش ۷ سند).
  - سفارش‌گیری آنلاین جدید: مسدود (دسترسی کامل مدیریتی محدود می‌شود).
  - پس از تمدید: همه‌چیز بلافاصله برمی‌گردد.
- **ترِیال:** انقضای تریال = همان حالت «انقضا» با فاز `TRIAL_OVER`؛ نمایش شمارش معکوس.
- صفحات فروش/قیمت/تلگرام فعلی (لایسنس پرایسینگ) **سراسریِ سازنده** می‌مانند و به هر مجموعه نمایش داده می‌شوند.
- دفتر فروش قدیمی (`LicenseSale`/`LicenseCharge`) به‌عنوان آرشیو حفظ می‌شود؛ سیستم جدید `License`+`LicenseEvent` است.

## ۳) پنل مدیریت کل (Super Admin)

- بخش جدید `SuperAdminView` — فقط برای `SUPER_ADMIN` (گیت سمت سرور `requireSuperAdmin` = role + `isOwnerMobile`).
- تب‌ها:
  1. **مجموعه‌ها:** فهرست + جست‌وجو/فیلتر (نام، موبایل مدیر، وضعیت، وضعیت لایسنس، بازه انقضا) + جزئیات هر مجموعه.
  2. **جزئیات مجموعه:** مدیر مجموعه، کاربران، کالاها/گروه‌ها، مشتریان، سفارش‌ها/فاکتورها، گزارش فروش و مالی — **فقط مشاهده (read-only)** با همان کامپوننت‌های موجود در حالت org-scoped.
  3. **لایسنس:** صدور/تمدید/تعلیق/فعال‌سازی مجدد + تاریخ شروع/پایان + سوابق (`LicenseEvent`).
  4. **پشتیبانی:** صندوق پیام‌ها (بخش ۴).
  5. **لاگ دسترسی:** `AdminAccessLog`.
- **حسابرسی دسترسی سازنده:**

```prisma
model AdminAccessLog {
  id        String   @id @default(cuid())
  actorId   String
  actorName String
  orgId     String?   // مجموعه مورد مشاهده
  action    String    // VIEW_ORG | VIEW_USERS | VIEW_ORDERS | VIEW_REPORTS | ISSUE_LICENSE | ...
  detail    String?   // JSON بدون داده حساس
  ip        String?
  createdAt DateTime @default(now())

  @@index([orgId, createdAt])
  @@index([actorId, createdAt])
}
```

- هر اندپوینت `/api/sa/*` پیش از پاسخ، لاگ می‌نویسد. **رمز عبور هیچ‌گاه نمایش داده نمی‌شود** (هش scrypt هرگز سریالایز نمی‌شود).
- سیاست حریم خصوصی: متن شفاف در صفحه «درباره/تنظیمات» + همین سند: «سازنده امکان مشاهده اطلاعات مجموعه‌ها برای پشتیبانی را دارد و این دسترسی‌ها ثبت می‌شوند».

## ۴) پشتیبانی داخلی

### ۴.۱ مدل

```prisma
model SupportThread {
  id             String   @id @default(cuid())
  orgId          String
  org            Org      @relation(fields: [orgId], references: [id], onDelete: Cascade)
  subjectType    String   @default("GENERAL") // GENERAL | BUY_LICENSE | RENEW
  status         String   @default("OPEN")    // OPEN | ANSWERED | CLOSED
  unreadForOrg   Boolean  @default(false)
  unreadForVendor Boolean @default(true)
  lastMessageAt  DateTime @default(now())
  createdAt      DateTime @default(now())
  messages       SupportMessage[]

  @@index([orgId, lastMessageAt])
}

model SupportMessage {
  id          String   @id @default(cuid())
  threadId    String
  thread      SupportThread @relation(fields: [threadId], references: [id], onDelete: Cascade)
  senderSide  String   // ORG | VENDOR
  senderName  String
  body        String
  clientRef   String?  // UUID کلاینت برای ارسال آفلاین idempotent (یکتا روی thread)
  createdAt   DateTime @default(now())

  @@unique([threadId, clientRef])
}
```

### ۴.۲ رفتار
- **مشتری:** ساخت رشته (نوع درخواست: خرید لایسنس/تمدید/عمومی)، ارسال پیام متنی، **شناسه مجموعه به‌صورت خودکار** پیوست می‌شود، مشاهده وضعیت (OPEN/ANSWERED/CLOSED) و پاسخ سازنده؛ نشان خوانده/نخوانده دوطرفه (فلگ‌های denormalized).
- **سازنده:** صندوق در پنل Super Admin — فهرست همه پیام‌ها با نام/شناسه مجموعه + مدیر مجموعه + تاریخ، پاسخ، تعیین وضعیت، خوانده/نخوانده.
- **قطعی اینترنت:** پیام در صف محلی (IndexedDB) با وضعیت «در انتظار ارسال» ذخیره؛ خودکار ارسال پس از اتصال؛ **تا ack سرور (clientRef ثبت‌شده) از صف حذف نمی‌شود.**
- ارتباط فقط از طریق سرور ایرانی (بدون وابستگی به تلگرام)؛ آیدی تلگرام سازنده فقط به‌عنوان مسیر جایگزین در صفحه پشتیبانی و صفحه فعال‌سازی لایسنس نمایش داده می‌شود (تنظیم فعلی `support_telegram` حفظ می‌شود) + فیلد شماره تماس/پیامک جدید در تنظیمات سازنده (قابل تغییر از پنل).
- **مستقل از اینترنت بین‌الملل:** فونت Vazirmatn از CDN به `public/` self-host منتقل می‌شود (الان از jsDelivr است — تک‌مورد وابستگی بین‌المللی UI).

## ۵) حالت آفلاین

### ۵.۱ لایه‌های ذخیره‌سازی (همه جدید — در ممیزی هیچ‌کدام وجود نداشت)

| لایه | فناوری | محتوا |
|---|---|---|
| پوسته برنامه | **Service Worker** (precache HTML/JS/CSS/فونت/آیکون‌ها) | بارگذاری برنامه بدون شبکه |
| اسنپ‌شات داده | **IndexedDB** (`vizito-db`) | آخرین همگام‌سازی: مشتریان، کالاها، گروه‌ها، قیمت‌ها/تخفیف‌ها، تنظیمات مجموعه، لوگو، وضعیت لایسنس — به‌همراه `syncedAt` |
| صف خروجی (Outbox) | IndexedDB | سفارش‌های آفلاین + پیام‌های پشتیبانی در انتظار ارسال |
| هویت دستگاه | UUID در localStorage + هدر `X-Vizito-Device` | ثبت در جدول `Device` سمت سرور (orgId، userId، آخرین حضور) |

### ۵.۲ مجاز/ممنوع در آفلاین (رعایت دقیق بخش ۷ سند)
- **مجاز:** مشاهده همه داده‌های همگام‌شده؛ سفارش‌گیری فقط از مشتریان/کالاهای همگام‌شده‌ی همان مجموعه؛ صدور فاکتور؛ تولید PDF (خط PDF فعلی کاملاً کلاینت-محور است — html2canvas+jsPDF — پس آفلاین کار می‌کند)؛ مشاهده سفارش‌های آفلاین ثبت‌شده.
- **ممنوع (UI قفل می‌کند و سرور هم رد می‌کند):** ثبت/ویرایش مشتری، کالا، گروه، قیمت، تخفیف، کاربر، تنظیمات.

### ۵.۳ قواعد سفارش آفلاین
- قیمت‌ها/مشخصات از آخرین اسنپ‌شات دستگاه **منجمد** در `OrderItem` می‌شوند (همان ساختار denormalized فعلی — تاریخچه با تغییرات بعدی بازنویسی نمی‌شود).
- هر سفارش: `clientRef` (UUID یکتای سراسری، `@unique`) + `deviceId` + `orgId` + `createdOffline=true` + `syncedAt=null`.
- ذخیره پایدار در IndexedDB؛ بستن برنامه/خاموشی حذف نمی‌کند؛ وضعیت «در انتظار همگام‌سازی» تا ack سرور.
- فاکتور آفلاین با برچسب «ثبت‌شده در حالت آفلاین» (روی فاکتور و PDF).

### ۵.۴ آفلاین پس از انقضای لایسنس
- همان قابلیت‌های ۵.۲ بدون تغییر (نمایش + سفارش‌گیری + PDF).
- پس از اتصال: وضعیت لایسنس از سرور بررسی؛ اگر منقضی باشد، **همگام‌سازی سفارش‌های آفلاین پذیرفته می‌شود**، ولی عملیات مدیریتی جدید مسدود می‌ماند؛ داده‌ها هرگز حذف نمی‌شوند (D2).

## ۶) همگام‌سازی چند دستگاه

### ۶.۱ پروتکل
```
GET  /api/sync/bundle?since=ISO        → اسنپ‌شات org-scoped (فقط مجموعه خود) + نسخه داده
POST /api/sync/orders                  → دسته‌ای (≤50) سفارش با clientRef
     پاسخ هر آیتم: {clientRef, orderId, result: ACCEPTED | DUPLICATE | REJECTED(reason)}
POST /api/sync/support                 → دسته‌ای پیام‌های پشتیبانی (همان الگوی clientRef)
```
- **Idempotency:** `clientRef @unique` روی Order — ارسال مجدد همان سفارش = `DUPLICATE` با شناسه موجود؛ **هیچ‌گاه دوباره درج نمی‌شود**.
- دستگاه‌های مستقل صف‌های مستقل دارند؛ سفارش‌های یکدیگر را بازنویسی/جایگزین نمی‌کنند (فقط درج).
- ارسال مجدد خودکار: در بازشدن برنامه + در رویداد reconnect + بک‌آف نمایی؛ نسخه محلی تا ack موفق باقی می‌ماند؛ خطاها در صف باقی + نمایش وضعیت به کاربر.
- **تعارض قیمت:** سرور قیمت آیتم آفلاین را با قیمت فعلی کالا مقایسه می‌کند؛ تفاوت ⇒ سفارش پذیرفته و `needsReview=true` می‌شود + اعلان به مدیر مجموعه (طبق سند: حذف/اصلاح خودکار ممنوع، فقط علامت‌گذاری).

## ۹) نقشه مهاجرت دیتابیس — امن، ترتیبی، بدون حذف

> اصل: فقط **افزودن**؛ هیچ DROP/DELETE/تغییر نوع؛ هیچ Reset؛ اجرا از طریق مهاجرت‌ساز خودکار موجود (`scripts/migrate-sqlite.cjs` بدون Prisma CLI) سازگار با cPanel.

| گام | محتوا | برگشت‌پذیری |
|---|---|---|
| M0 | بکاپ رمزشده کامل + کپی فایل DB (توسط ادمین، قبل از استقرار) | بازیابی کامل از بکاپ موجود |
| M1 | ایجاد جداول جدید: `Org, License, LicenseEvent, SupportThread, SupportMessage, Device, AdminAccessLog` + ایندکس‌ها | فقط CREATE — بی‌اثر بر داده |
| M2 | افزودن ستون‌های nullable: `User.orgId/role`، `Customer.orgId`، `ProductGroup.orgId`، `Product.orgId`، `Order.orgId/clientRef/deviceId/createdOffline/syncedAt/needsReview`، `Payment.orgId` + ایندکس‌های ترکیبی (`orgId+createdAt` و ...) | ستون‌های جدید nullable — هیچ ستونی حذف/تغییر نمی‌کند |
| M3 | **اسکریپت بک‌فیل Node (idempotent):** ساخت «مجموعه پیش‌فرض» از نصب فعلی → نسبت‌دادن `orgId` به همه ردیف‌ها → نگاشت نقش‌ها (مالک→SUPER_ADMIN، ADMIN→ORG_ADMIN، بقیه→VISITOR با حفظ AccessGrant) → ساخت License مجموعه پیش‌فرض مطابق وضعیت لایسنس فعلی (فعال/دائمی) → مهاجرت `app_logo/invite_code` به Org | اسکریپت فقط INSERT/UPDATE افزونه؛ قابل اجرای مجدد؛ قبل/بعد با شمارش رکوردها صحت‌سنجی می‌شود (۱۷ جدول) |
| M4 | فعال‌سازی `PRAGMA journal_mode=WAL` + `busy_timeout` در لایه اتصال | برگشت‌پذیر با restart |

- **قید یکپارچگی:** `orgId` در نسخه اول nullable می‌ماند و کامل‌بودن آن با اسکریپت صحت‌سنجی (بعد از M3: صفر ردیف بدون orgId در جداول تجاری) تضمین می‌شود؛ سخت‌گیرکردن NOT NULL عمداً به نسخه بعد موکول شد (SQLite برای آن نیاز به بازسازی جدول دارد — ریسک بی‌مورد).
- داده کاربران PUBLIC فعلی/ترِیال شخصی: حفظ کامل (بدون حذف؛ تا اولین لایسنس، همان قفل فعلی).
- دفتر فروش قدیمی و همه Settingهای سراسری: حفظ.

## ۱۰) امنیت (تکمیلی بخش دهم سند)

- رمزها: scrypt (بدون تغییر)؛ نشست‌ها: کوکی HttpOnly (بدون تغییر)؛ APIهای جدید همه پشت `requireAuth`/`requireSuperAdmin` + CSRF gate + لیمیت (sync: 30/min، support: 10/min — پایدار در DB).
- اعتبارسنجی ورودی: سقف طول بدنه پشتیبانی (4000)، سقف دسته sync (۵۰)، اعتبارسنجی clientRef (UUID)، هویت دستگاه (رشته ≤64)؛ بدون `$queryRaw`.
- ایزوله‌سازی: هیچ مسیری orgId را از کلاینت نمی‌پذیرد؛ 404-masking بین مجموعه‌ها؛ سریالایزرهای Super Admin هش رمز/توکن را حذف می‌کنند.
- دستگاه: UUID فقط شناسه است (نه اعتبارنامه)؛ نشست همچنان کوکی.
- آپلود تصویر: همان اعتبارسنجی data-URL فعلی (PNG/JPEG/WEBP، سقف حجم) برای لوگوی مجموعه.
- لاگ‌ها: بدون داده حساس (ادامه قاعده فعلی).
- **بکاپ/بازیابی:** خوراک بکاپ به جداول جدید گسترش می‌یابد؛ **Restore جدید:** آپلود پاکت رمزشده → تأیید هش/نسخه → نمایش پیش‌نمایش شمارش‌ها → تأیید دو مرحله‌ای (رمز ادمین + تایپ نام) → جایگزینی تراکنشی؛ فقط admin/سازنده — و واقعاً آزمایش می‌شود (بخش دهم).
- خروج کاربر: پاک‌سازی کش IndexedDB محلی و محافظت داده‌های مجموعه از حساب بعدی (event logout → `idb.clear()` + SW cache purge).

## ۱۱) عملکرد و ظرفیت

- WAL + `busy_timeout=5000` + تراکنش‌های کوتاه؛ ایندکس‌های `orgId(+createdAt)` روی جداول داغ؛ صفحه‌بندی موجود حفظ.
- اندازه: سقف تصویر فعلی (2.5MB) می‌ماند؛ توصیه آینده: انتقال تصاویر به فایل‌سیستم (گزینه در ضمیمه).
- باندل: `next/dynamic` برای SuperAdmin/گزارش‌ها (کاهش باندل اولیه)؛ حذف وابستگی‌های مرده اختیاری و جدا از این پروژه (فهرست در ممیزی).
- تست بار واقعی در مرحله ۹ انجام می‌شود (سفارش‌گیری هم‌زمان چند دستگاه شبیه‌سازی‌شده).

## ۱۲) ترتیب پیاده‌سازی (پس از تأیید — معادل مراحل ۳ تا ۹ سند)

1. **چندمجموعه‌ای:** M1→M4 + ctx.org + scoping همه APIها + ثبت‌نام/Org + نقش‌ها + تنظیمات مجموعه.
2. **لایسنس:** VZT3 + License/LicenseEvent + فازها/تعلیق/تمدید + غیرفعال‌سازی sweep (D2) + صفحه لایسنس مجموعه.
3. **Super Admin:** `/api/sa/*` + AdminAccessLog + SuperAdminView + حریم خصوصی.
4. **پشتیبانی:** مدل‌ها + `/api/support/*` + صندوق سازنده + صف آفلاین پیام + تنظیمات تماس.
5. **آفلاین:** SW + IDB store + کوهورت اسنپ‌شات + قفل فرم‌ها + سفارش آفلاین + PDF + برچسب «ثبت‌شده در حالت آفلاین».

7. **تست نهایی:** ایزوله (final-e2e جدید: ایزوله‌سازی مجموعه‌ها، ماتریس لایسنس، idempotency، تعارض، انقضا+آفلاین، پشتیبانی، بکاپ/بازیابی) + سناریوهای سند (چنددستگاه، لایسنس منقضی، قطعی کامل دوگانه) + APK واقعی.

## ضمیمه الف — Runbook مهاجرت آینده به MariaDB (فقط در صورت رشد)
